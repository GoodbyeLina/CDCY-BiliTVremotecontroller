## 1. 当前基线与范围

- 三代目标：Kotlin 原生 Android App，手机负责内容管理、播放编排及媒体转发，电视通过 mpv 播放。
- 当前根工程为 `:core` + `:app` 双模块；`:app`（包名 `tvrc.app`，versionName `3.0.0-alpha.1`）首版已可构建，产物 `dist/TVStationRemote-3.0.0-alpha.1-debug.apk`。仓库的 `TVStationRemote-0.2.0.apk` 仍是依赖 Termux 的旧版。
- 2026-11-20 回归：`:core:test` 23 个测试类 184 条通过、0 失败（历史基线 170 条 + 新增短链展开/播放状态探针 14 条）；`:app:assembleDebug` 构建成功。自动化通过不等于真机验收通过。
- 用户反馈既有播放业务测试无明显问题。尽量复用现有核心；补齐调用链与缺失能力，并保持回归通过。
- 标准视频/直播网页网址与 `b23.tv` 短链均由 `ShareText`+`SourceExpander` 提取并跟随有界重定向后再分类（`core/.../bili/ShortLink.kt`）；合集/系列由 `LinkImporter` 展开成分集/整组队列。
- 本轮只整理需求，不宣称实现了下列功能。已有交互原型用于讨论，不是 Android 运行截图；视觉细节仍可调整。

状态：**部分完成**＝已有相关模块但链路不完整；**已有待验证**＝存在实现，仍缺设备证据；**未实现**＝尚无完整功能；**后续评估**＝不列为首版完成条件。

优先级：**P0**＝独立可用版本的前置条件；**P1**＝本轮完整功能范围；**P2**＝后续优化。阶段表示建议开发顺序，不代表删减 P1 需求。

## 3. 用户提供的解析回归样例

记录内容标识即可，不保留原网址里的跟踪参数值。

| 样例 | 输入 | 预期 |
|---|---|---|
| V1：电脑视频网页 | `https://www.bilibili.com/video/BV15H45zUE7T/?spm_id_from=example&vd_source=example` | `Video(BV15H45zUE7T)`；带参数、无参数、纯 BV 三种形式一致 |
| L1：电脑直播网页 | `https://live.bilibili.com/612978?live_from=82002&spm_id_from=example` | `LiveRoom(612978)`；随后查询并确认实际直播间信息 |
| S1：手机分享文案 | `【AI圈裂开！从Gemini 4 Krypton疯狂改口Oxygen，同题测试Hydrogen xhigh被反超，谷歌还在发力！-哔哩哔哩】 https://b23.tv/ZSX0hxs` | 提取并展开短链；2026-11-16 实际跳转视频为 `BV1Atsc6gEbb`，与 V1 是不同视频 |

本轮已经用仓库内现有编译产物调用 `SourceParser`：V1→Video、L1→LiveRoom、S1→ShortLink。该检查只证明分类，**没有证明 App 入口、短链展开、获取播放地址或电视播放成功**。S1 的跳转目标做过只读联网验证；未来访问失效应归类为网络/链接失效，不能混同解析器回归。

补充验收矩阵：前后文字、换行、中文标点、重复粘贴、空输入、非法地址、短链超时/循环；合集分页、空合集、不可用条目。具体失败版本尚未提供，不能把旧版与三代混作同一故障。

## 4. 已确认的前端方向

1. **内容库是首页**：视频与合集 / 直播间双分类，顶部导入，支持搜索、最近看过、收藏。列表项显示封面、标题、UP 主及来源类型。
2. **导入不等于播放**：解析成功先预览、保存；需要用户选择播放。内容长期保留，历史按真实播放记录产生。
3. **节目单独立管理**：先组合内容、确定顺序，再建立一次或周期播放任务；定时任务引用节目单。
4. **开播规则按房间设置**：通知、自动播放、唤醒、下播恢复、优先级、覆盖手动停止均为明确选项。
5. **设备与向导**：手动唤醒、连接检查、授权与播放器检查、真实试播；不要把模拟成功或“已发命令”当作设备验证。

已展示原型的页结构为“内容库 / 节目单 / 开播监控 / 设备”。原型包含模拟导入、定时、开播/下播及向导动作，但不是可安装 App，也没有实际控制外部设备。视觉样式仍属待迭代设计，不把本轮配色、布局间距视为最终批准稿。

## 5. 监控与定时技术方案

### 5.1 保留与新增

| 部分 | 方案 | 说明 |
|---|---|---|
| 已有基础 | Kotlin `:core`、状态机、HTTP 代理、自研 ADB、B站 HTTP 接口 | 复用并补齐集成；不因增加监控重写全部业务 |
| Android 应用 | Compose、ViewModel/StateFlow、协程、前台服务 | 所有阻塞网络/ADB 操作离开主线程；界面与通知读取统一状态 |
| 内容与任务持久化 | 建议新增 Room | 存内容、观看历史、节目单、定时任务、关注规则；基础设置 JSON 保留迁移路径。此为实现建议，非用户指定库 |
| 每日定时 | AlarmManager + 接收器 + 前台服务执行 | WorkManager 不承担精确时刻触发；按系统版本处理精确定时许可和后台启动约束 |
| 低实时性维护 | 可用 WorkManager | 用于允许延迟的维护；不承担秒级开播发现或固定时刻播放 |
| 本地开播通知 | Android 通知渠道 | App 发现开播后通知；不声称订阅了官方推送 |
| 长连接 | P2 实验 | 先验证协议、离线开播事件与耗电收益，再决定是否上线 |
| 服务器监控/推送 | 暂不引入 | 若未来要求手机 App 被终止后仍接收外部通知，再独立评估；推送到达不保证后台自动播放 |

### 5.2 自适应轮询约束

- **已经确认的方向**：本地自适应轮询作为基础，直播消息长连接作为后续优化，不固定为全天所有直播间持续高频查询。
- 只查用户主动关注的房间。重点/常见开播时段可从 30–60 秒间隔起步；其他时段降到分钟级或按设置暂停。**具体默认间隔仍需根据延迟与耗电实测确定**。
- 集中调度、连接复用、有界并发；若有可用批量接口，先验证再使用，不能假定一定存在。
- 网络或接口失败逐步退避；成功后恢复正常频率。状态未知时保留上次成功值和时间，不生成虚假的开播/下播事件。
- 每次开播生成稳定事件标识去重；重连、进程恢复以及长连接与轮询并用时都不能重复抢播。
- 监控停止或移除关注后取消对应任务。界面显示监控是否有效，避免仅显示“已开启”而后台实际未运行。
- 提交验证数据：关注数量、间隔、请求次数、网络状态、息屏时长、发现延迟分布、耗电情况及测试设备；不预先承诺普适的耗电百分比。

### 5.3 唤醒和执行边界

- ADB 唤醒适用于电视保持局域网、adbd 可达且已经授权的待机状态。完全关机、断网或深度休眠不承诺可唤醒；先在目标电视验证，再决定是否需要 WOL 或其他方案。
- 定时任务采用手机当前时区。错过触发时默认只记录失败/错过，不在任意时间突然补播；是否允许在宽限时间内补播为待定项。
- 前台服务不能保证所有厂商 ROM 永不杀进程；用户强行停止 App 后，系统任务也可能停止，需重新打开。不能承诺在这类状态下照常自动播放。
- 抢播统一走播放编排器，不绕开状态机直接发 ADB。优先级初步为“显式用户操作优先；被授权的重点直播可中断普通节目单”；同级冲突稳定排序、不振荡。
- “下播恢复”首版要求恢复原节目单和条目位置；精确到秒续播取决于播放器可靠接口，单独验收，不做无依据承诺。

| 直播监控目标 | 主动关注、少量房间 | 目标数量与可接受发现延迟，用于确定请求与耗电预算 |
| 精确定时与错过任务 | 按手机时区；错过不自动补播 | 是否允许补播宽限、跨时区保持绝对时刻或本地钟点 |
| 强制播放 | 每房间明确授权；默认不覆盖手动停止 | 哪些重点直播可打断用户操作，以及同优先级冲突规则 |
| 历史续播 | 可重新播放，恢复队列条目 | 是否必须恢复到秒级进度，需验证 mpv 控制能力 |
| 目标手机与电视 | Android 原生手机＋支持 ADB 的电视 | 系统版本、ROM、待机网络行为与播放器版本 |
| 真实故障环境 | 已提供 3 条输入样例 | 发生故障的 APK 版本、对应错误提示；用于复现实际入口故障 |
