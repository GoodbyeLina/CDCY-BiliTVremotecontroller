# 播放异常？从这里开始

适用：**3.0.0-alpha.6**。不需要懂网络，先找现象，只读对应的小节。

> **三句话：**接受命令不等于已出画面；首批数据不等于首帧；有传输速度不等于画面流畅。

## 快速入口

| 你看到的现象 | 去哪里 |
|---|---|
| 能播放，自检却超时 | [A · ADB](#a--adb-超时) |
| 点了播放一直等待 | [B · 没有媒体请求](#b--没有媒体请求) |
| 有数据，但黑屏、无声或其他音乐 | [C · 音画异常](#c--音画异常) |
| 403、410、429、来源读取中断 | [D · 报错速查](#d--报错速查) |
| 停止后复活、视频从头播放 | [E · 停止与进度](#e--停止与进度) |
| 还没解决 | [反馈模板](#反馈模板) |

## 先保存证据，再尝试修复

1. 记下发生时间、房间号/BV，以及电视实际画面和声音。
2. 在 App **设备页**找到诊断记录/导出诊断入口，异常后尽快导出文本文件。
3. 有电视错误提示时拍照。不要先清数据、卸载或反复重置授权。

诊断有容量上限：应用保存最近300条事件，导出取最近200条及日志尾部500行。连续做很多测试后再导出，早期证据可能已被覆盖。

> **隐私提醒：**完整导出包含配置、局域网 IP、内容标题，输入记录可能包含分享链接。新增媒体事件不记录签名直链，不代表整个文件已统一脱敏。公开上传前检查；遮盖个人信息时保留时间、报错、请求编号和房间/BV。

## 日志只看这条线

**播放请求 → 电视接受命令 → 电视请求媒体 → 来源响应 → 首批数据 → 持续传输**

导出中的最近事件通常是**新到旧**排列；先找异常时间，再向前串联。同一个“请求 #编号”属于同一次媒体请求，快进、切台可能产生新编号。

| 字段/事件 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 电视回执成功 | 拉起命令被接受 | 已显示画面 |
| 媒体请求 | 有客户端请求手机代理 | 已有音画 |
| HTTP 响应 | 来源返回该状态码 | 内容一定可解码 |
| 首批数据 | 代理向电视连接写入了媒体字节 | 已出首帧、电视已收到并解码 |
| 已发送字节/速度 | 本次累计写入量及自请求开始的平均速率 | 实时网速、画面流畅度 |
| 传输结束 | 本次连接读取完成 | 整部视频播完或直播正常下播 |
| headOnly=true（如在详情中可见）/HEAD请求 | 播放器探测，不传媒体正文 | 首帧或完整播放 |
| 网络类型变化 | 手机默认网络类型改变 | 网络质量或电视到手机可达性 |
| ADB采样失败 | 控制检查失败 | 媒体必定停止 |

媒体请求编号不覆盖所有播放/ADB事件；结合时间和内容标识看，不强行把不同请求拼成一次。

## A · ADB 超时

**先别卸载 mpv。**播放器“需先连接并授权”可能只是未能完成安装检查，不等于没安装。

- [ ] 核对设备页电视 IP、端口与电视当前地址一致。
- [ ] 手机和电视在同一局域网，非访客隔离网络。
- [ ] 电视出现调试授权时选择允许；没有弹窗不证明授权失败。
- [ ] 视频正在播放时只执行一次自检，等结果，不连续点击。
- [ ] 再试停止：若能控制，却仍报超时，保存完整阶段提示并反馈。

**可能原因（不是结论）：**地址变化、网络/握手未响应、等待授权、控制通道繁忙。
“首包未收到”“已发送签名”“公钥待授权”表示超时发生阶段，不单独证明根因。alpha.6 自检优先借用同目标传输层；即使借用也可能超时。

## B · 没有媒体请求

现象：已有“电视回执”，但对应时段找不到媒体请求。

- [ ] 看电视是否打开 mpv，有无报错，先拍照。
- [ ] 核对配置中的手机代理地址和端口；不能给电视使用127.0.0.1。
- [ ] 手机切换网络后地址可能变化；检查是否仍是电视可达的局域网地址。
- [ ] 确认手机前台播放服务仍在，后台/省电限制有无关闭服务。
- [ ] 若仍失败，提交时间、配置中地址（私下提供）、电视提示及日志。

**可能原因：**播放器未打开、手机代理地址不可达、网络隔离、服务停止。日志缺失也可能是滚动覆盖，不能仅凭“没看到”判定电视从未请求。

## C · 音画异常

现象：有首批数据/传输记录，但黑屏、无声、错误音乐或其他内容。

- [ ] 记录电视前台应用及错误提示；不要只描述“不能播”。
- [ ] 用遥控器检查暂停、静音和音量，稍等缓冲。
- [ ] 直播在手机 B站打开同一房间，对照当前音画及开播状态。
- [ ] 核对实际房间/BV是否就是本次选择的内容；看是否有新切台/监控抢播事件。
- [ ] 换一个正常视频/直播间进行对照，分别记录结果。

**可能原因：**内容本身异常、缓冲/解码/播放器状态、错误前台应用或会话选择等。代理数据正常不能单独排除网络，也不能直接认定 mpv 故障。
alpha.5 已移除全局播放/暂停键并修复新增直播允许列表；**现场随机音乐的唯一根因仍未证实**。

## D · 报错速查

| 提示/分类 | 可能原因 | Checklist：先做什么 |
|---|---|---|
| 解析播放地址失败 / RESOLVE | 内容不可用、接口失败、手机网络异常 | 确认手机能打开相同内容；直播确认开播；稍后再试 |
| 401/403/410 | 访问受限或地址失效 | 等有限刷新结果；仍失败换内容/稍后试，不断言账号有问题 |
| 429 | 来源限频 | 停止连续点击，稍后再试 |
| 408/5xx | 来源或链路临时异常 | 等有限重试；仍失败保存HTTP状态与时间 |
| UPSTREAM_OPEN | 手机无法连接来源 | 检查手机网络；对照手机B站；不要只检查电视ADB |
| UPSTREAM_READ | 来源读取中断 | 记录断流时间；检查手机网络；视频不静默从头重播，直播确认开播后可手动重试 |
| CLIENT_WRITE / 电视关闭连接 | 停止、快进、切台，也可能连接断开 | 刚做过这些操作且播放正常，无需处理；否则保存当时操作和电视现象 |
| SERVER_CLOSED / 取消 | 用户停止或代理关闭 | 主动停止时正常；非主动操作则检查服务是否结束 |
| 400 / 房间拒绝（可能是下游响应） | 房间格式/授权范围不匹配 | 核对房间号；从内容库重新选择；新增房间持续失败则反馈，不改源码白名单 |
| INTERNAL / 其他 | 尚未分类的异常 | 保存请求编号、异常类型、时间与完整诊断 |

**重试边界：**只在媒体响应尚未提交前，对适合的临时故障最多额外重试两次；403/410最多重新解析一次。两类条件组合时不能把“最多两次”当作所有原因合计的全局次数。HEAD不自动重试。传输开始后的失败不自动从头重开点播。

## E · 停止与进度

- [ ] 确认没有手动再次播放、到点节目单或明确允许覆盖停止的监控任务。
- [ ] 记录停止/重新出现画面的准确时间、此前是否正在等待解析。
- [ ] 记录快进前后位置，是否确实回到开头，还是新媒体请求而画面正常。
- [ ] 若无合理触发却复活、从头重播，视为需要反馈的问题，不用“重试正常”覆盖失败结果。

短暂无流量可能来自暂停、预缓冲或快进；本版不以此直接判卡顿。直播连续三次失联才进入有限恢复，累计上限三次、60秒冷却；点播失联提示错误，不静默重开。进程/ADB布尔探针仍不能代表真实画面。
